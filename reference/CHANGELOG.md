# Changelog

Notable changes to the CIS Warehouse Portal, tracked here as of 2026-08-14. Full behavioral/data contract detail for anything below lives in [`SCHEMA.md`](./SCHEMA.md) — this file is a running record of *what changed and why*, not the operational reference.

## 2026-08-27 — Shipping Estimator / Guided RTS: Literal Destination Picker, Ports Ranked Fastest-First (UX)

Source: user — "the shipping estimator and RTS tool are confusing. The destination should be changed from the port cluster to the literal destination; from there the actual ports should display like they do currently, ordered fastest to slowest."

### Changed

- **The Destination dropdown now lists the literal receiving docks, not the `Transit_Time` regional clusters.** It used to show `"Ontario (GTA)"`, `"Alberta (Edmonton)"`, `"Florida (US East)"`, `"Victoria (AU)"` — the clustering the lane table was reconciled into 2026-08-19. It now shows the real destinations from the `Delivery_Address` tab (RTF — Orangeville, BUNZL Burlington, TJX DC (TDC), CAVALIER (RTF storage), BUNZL Edmonton, CREDO, CIS Security Solutions), each mapped back to its cluster for the actual lane math by a new explicit `DELIVERY_DESTINATION_CLUSTERS` table (`Service_Dates.js`) — keyed by the exact `Delivery_Address.Destination` string, **not** fuzzy dock-name matching (that pattern has caused real ETA bugs here — the CAVALIER/RTF and "Los Angeles" collisions). Docks that share a cluster (RTF / BUNZL Burlington / TDC / CAVALIER all → Ontario) show identical numbers by design, confirmed with the user. `getTransitLaneCatalog()` gained a `deliveryDestinations` array; a `Delivery_Address` row with no map entry is logged and left out; a cluster with lanes but no dock is kept reachable via a self-entry. Applies to both places the guided flow appears — the inline Readiness & ETA panel and the standalone Shipping Estimate calculator (they share the cascading-dropdown helpers in `JS_Handlers.html`).
- **The Port dropdown is now ordered fastest → slowest, and each option shows its estimate** — e.g. `"Prince Rupert · ~53 days"`, `"Vancouver · ~58 days"`. The number is that port's worst case (max `Total_Est_Days` across its load types and both seasons), which is the same figure the engine's slowest-wins default resolves to, so the ranking matches the ETA that appears once a ship date is entered. The option's saved value is still the bare port name — `portOfArrival` and every server-side match are unchanged. Nothing new is persisted; as before, only the resolved Port is written to the row.

### Internal

- `resolveTransitDestinationCluster_()` (server, wired into `findTransitLane_()`) and `resolveDestinationCluster_()` (client) translate a literal destination back to its cluster before any lane lookup; both are no-ops for a value that's already a cluster, so `estimateShippingWindowV2` / `estimateShipByDateV2` / saved `portOfArrival` values keep working with no migration. Full detail in `SCHEMA.md` §4G.

## 2026-08-27 — Outbound Staging Removal, Adjust Popup Rewrite, Drawer Refresh Fixes, Nav Restructure, Mobile Layout Bugs (Bug Fix / UX)

Source: user screenshots (iPhone 17 Pro, Chrome/iOS) reporting a floating/detached search bar, a clipped Open Slots layout on mobile, a station-name prompt that re-asked on every load, and an overloaded Warehouse Operations menu — plus a follow-up on the drawer not visibly updating after a quantity change, and the Adjust popup's SET-overwrite warning being "grossly huge."

### Removed

- **Outbound Staging Aggregator / the `ZONE-STAGED` virtual location, entirely.** Its original intent was only ever a status change (recolor the pallet's slot, deduct it from Inventory Totals' "available" pool) — both of which `renderLabels()` and `generateLocalTotals()` already did off a row's Workflow Status. The zone actively defeated that: moving a pallet to `ZONE-STAGED` emptied its rack slot instead of recoloring it in place. Both STAGED controls (the drawer's move-carry-bar and each accordion card's quick-action) now call `updateItemField(...,'status','Staged',...)` in place instead of moving the row. Deleted `View_Staged.html`, `renderStagedView()`, the nav entry, and `ZONE-STAGED` from `VIRTUAL_ZONES` (`Service_Write.js`, both `moveInventoryItem`/`moveHubGroup`). Confirmed via the `CIS INVENTORY.xlsx` snapshot before deleting: exactly one `ZONE-STAGED` row, at qty 0 — nothing was stranded.
- **The Station ID prompt, entirely** (not just the on-load version fixed further down). This app is `ANYONE_ANONYMOUS` with no login to key an identity to, running inside a cross-origin `googleusercontent.com` iframe where iOS WebKit can partition or block client storage outright — so no client-storage-based "remember this device" mechanism can ever be durable here, only ever a nag that resurfaces unpredictably. User's call on hearing that: drop it rather than ship something unreliable that reads as a broken app. Removed the prompt, the `getStationId_`/`setStationId_`/`ensureStationId_` helpers, and the `stationId` field from both the receiving payload and the Audit_Log tag (`receivePOCardItems`, `Service_Write.js`). If per-device attribution is wanted later, it needs to travel in the URL (a `?station=` query param on each device's bookmark, read in `doGet`) — the only mechanism in this deployment that survives a storage wipe.

### Fixed

- **The Adjust popup's Workflow Status dropdown now decides split-vs-whole-row for itself** (`applyRowStatus_`, `JS_Handlers.html`) instead of relying on a separate manual "SPLIT INTO NEW ROW" button and a red SET-overwrite warning banner. Staging less than the row's full quantity now auto-splits the typed amount into a new row at the same location with the picked status, leaving the remainder at its old status; staging the whole amount (or leaving the qty box empty) still changes the whole row's status the old way. SET itself is unchanged (a plain recount) — the warning is gone because the destructive keystroke pattern it existed for (SET + a smaller number silently erasing the difference) can no longer happen through this popup at all.
- **The drawer's quantity not visibly updating after SET/±/status/split**, three stacked causes in the single mutation funnel (`runMutation`, `JS_State.html`): (1) a post-write forced refresh was silently dropped if the 30-second background poll was already mid-flight for that dataset — and that in-flight read predated the write, so it landed with the stale number and nothing re-fetched on its own; now queued and drained the moment the in-flight fetch finishes. (2) The drawer repaint was skipped whenever `window.isEditing` was still true, which a `<select>`'s `onchange` can be (it fires before any blur); `runMutation` now clears it up front, mirroring `updateItemField`'s existing precedent. (3) The Adjust popup's own "Current Volume" line never updated in place after `setTotal`/`adjustStock` succeeded — only `splitOffQty` used to close the popup — now it updates optimistically, or closes if the row hit zero. Also added one floating "Saving…" indicator (`#mutation-busy-pill`) covering every drawer mutation, since they all already funnel through `runMutation`.
- **The search bar rendering detached over page content on iOS.** Not a `#top-ui` positioning bug — the keyboard-focus scroll helper (`JS_Store.html`) called `el.scrollIntoView({block:'center'})`, which scrolls every scrollable ancestor including `document.body`. `body` is `overflow:hidden` by design so it never scrolls under normal use, but `overflow:hidden` still accepts a programmatic `scrollTop`, and on iOS WebKit that produced a visible split-render glitch with the sticky header. Rewrote it to find and scroll only the one real scrolling ancestor of the focused field (e.g. `#audit-view`, the Adjust popup's `#adjust-qty-content`), so `body`'s scroll position can no longer be touched by this at all.
- **Open Slots reading as half-centered on mobile, with the P&P metric card clipped off the right edge.** Root cause: `.map-view:not(#totals-view):not(#hts-view)...` (`Styles_Base.html`) was a hand-maintained CSS exclusion list deciding which views get flex-centered, duplicated by a *separate* hand-maintained id list in `changeView()` (`JS_Render_Core.html`) deciding `display:flex` vs `block` — the two had already drifted from each other and from reality (`open-slots-view` and `wall-audit-view` were missing from the CSS list, so both got centered like an SVG floor plan instead of laid out top-down). Replaced both lists with two shared classes, `.floor-plan-view` (real SWH/PWH/P&P maps — centers) and `.flex-doc-view` (Open Slots, Inventory Totals — need their own internal flex-column but not centering); every other document view now needs neither, with plain `display:block` as the default instead of something to opt into. Also fixed `.metrics-row-wrapper`'s padding stacking on top of its parent's own padding (no `flex-wrap`, which is what clipped the P&P card), and `#open-slots-drilldown-panel`'s `width:calc(100% - 40px)` double-insetting for the same reason.
- **Rollup Status pills rendering at a different width per row** (e.g. "ORDERED" narrow, "ON THE WAY" wide in the same column), and wrapping mid-word ("ORDE"/"RED") on mobile. Factored into `renderStatusPill_()` (`JS_Handlers.html`): `display:block; width:100%` inside the table cell means every pill in a column now shares the column's width instead of hugging its own text, and `word-break`/`overflow-wrap` are reset to `normal` to override the mobile rule that was breaking words wherever needed to fit rather than only at whitespace.

### Changed

- **Reorganized the Warehouse Operations nav menu** (`Index.html`): CIS Warehouses (SWH/PWH/P&P, now also holding Temp Storage — folded in from a separate top-level entry, since it's a real CIS location, not "elsewhere") → Timing Lot → RTF Lot → Inventory Audit (new group: QB Audit + "Warehouse Audit," renamed from "Wall-to-Wall Audit" as a display label only) → Open Slots. Standardized `.menu-item` styling — replaced `justify-content:space-between` (which shoved a button's icon and label to opposite ends) with `align-items:center; gap:12px`, and moved each button's color/bold onto its icon only so every label reads the same weight and color. Also fixed `#view-menu`'s hardcoded `top:60px` overlapping the wrapped mobile search bar below 768px.

## 2026-08-17 — TJX Sub-Brands Still Collapsing to "TJX Cos." (Bug Fix)

Source: live bug-testing session — user reported the chain/brand filter "still broken for TJX items," everything getting caught up in generic "TJX Cos." The same-day precedence fix (below, "Assembly Consolidation & Chain/Brand Registry Fixes") only helps when the specific TJX CA/AU registry row's own regex actually matches — it doesn't help when the regex itself has a gap, which is exactly the case here.

### Fixed

- **`getChainFromRecord()` (`JS_Handlers.html`) had no keyword-fallback safety net**, unlike its sibling `classifyInboundOrderOrigin_()` (`JS_Render_UI.html`, Section 4E), which already has one for this exact class of problem: the registry's brand-oriented aliases don't catch every real card-naming pattern (documented example: the TJX-AU row's alias `TJX\s*(?:AUSTRALIA|AU)\b` can't match the literal live card name "TJX AUS Bulk Order" — no word boundary before the trailing `S` in `AUS`). Without a fallback, any card whose specific non-local registry row failed to match fell straight through to the bare `\bTJX\b` "TJX Cos." row in pass 2. Ported the same keyword list (`AUSTRALIA|AUS|TJX CANADA|TJXC|RTF GLOBAL|RTF|TJX AU|TJX TK|TJX UK`) into `getChainFromRecord()`, run between pass 1 and pass 2 so a non-local keyword signal still wins over the generic local bucket even when the registry regex itself is broken. The Canada branch looks up the real Parent_Account from the registry's `TJX-CA` row rather than hardcoding a guessed string, since that exact text isn't confirmed anywhere in code.
- **The `TJX AU` (Australia) registry row's own regex had the word-boundary bug described above, and was never actually fixed** — the 2026-08-17 `fixTjxCanadaAndTkMaxxRegistry()` repair only touched the TJX-CA rows and the TK-Maxx rows, not this one. Added a third fix to that same function: detects the bug at runtime (tests the row's live regex against a known "TJX AUS ..." sample) and corrects it to `\bTJX\s*(?:AUSTRALIA|AUS?)\b` only if still broken — safe to re-run.

## 2026-08-17 — Inbound Report "On Hand: no match" Despite Real Stock (Bug Fix)

Source: live bug-testing session — user reported "2 Alarm SMALL Scorpion Tag (90cm)" showing `On Hand: no match` on the Inbound Shipping Report despite having physical stock. Confirmed via Inventory Totals: 198 units genuinely on hand at `PWH-PandP-RACKD-SEC-01-L-04`, correctly labeled.

### Fixed

- **`findOnHandForItem_()` (`JS_Render_UI.html`) compared a nickname against a raw Product ID.** The report's item key is always resolved to the PRODUCT sheet's short nickname (`resolveCanonicalItemNameClient_`) before matching, but some Inventory rows' own `sku` field still holds the raw, long PRODUCT-sheet Product ID/description text rather than that same nickname (pre-2026-08-11 receipts, or any receiving path that skipped the canonical-name write) — so exact and substring matching could never line up even against a genuine match. Added a pass that resolves each Inventory row's `sku` through the same nickname lookup (`getNickname()`) before comparing, so both sides go through identical canonicalization.

### Known follow-up (stale sync, not a code bug)

- One PO's checklist line for this same product (PO 3587, "90cm 2 Alarm SMALL Scorpion Tag with a 90 cm length (35.43") with 0.83 mm diameter thinner cable") reports as its own separate 16,000-unit bucket instead of merging into the 146,500-unit one. Checked live on the actual Trello card: the checklist item DOES carry a `[NT525S/2AMF]` bracket now — it was one of the first cards tested with TrelloInjector and didn't originally, but has since been corrected on Trello. The portal doesn't read Trello live; it reads the `summary` column cached in the SHIPMENTS sheet, refreshed only by the real-time webhook or the scheduled `syncAllBoardsToShipmentsTab()` run — so this card's cached copy still holds the pre-bracket text until its next sync. Will self-resolve once that card re-syncs.
  - **Also worth checking**: `NT525S/2AMF` (no "90cm") is the Product ID for the *generic* "2 Alarm SMALL Scorpion Tag" nickname (1,161 avail), not "2 Alarm SMALL Scorpion Tag (90cm)" (198 avail) that the rest of the line's description is actually about. Once this card re-syncs, the line will merge into the generic bucket, not the 90cm one, unless the bracket is corrected to `NT525S/2AMF 90cm` — worth confirming which product this PO is really ordering before assuming re-sync alone fixes it.

## 2026-08-17 — `.ignore` Comment Backfill (Bug Fix)

Source: live bug-testing session — user pasted a rendered table row for a card ("Timing - Boot & Sleeve Count," Nicole POs) that still appeared on the dashboard despite having a `.ignore` comment. Traced to Trello directly: the comment (posted 2026-08-14 at 11:12 AM, exact text `.ignore`, a clean match for the parser) never resulted in the "PORTAL: IGNORE" label being applied.

### Fixed

- **The `.ignore`/`.unignore` comment trigger had no backfill/catch-up path.** The analogous READY/PORT feature has `backfillReadyPortFromComments_()` wired into every scheduled sync specifically to catch whatever its real-time webhook missed; `.ignore` never got the same protection, so any missed webhook (this comment likely predated that day's deploy) was lost permanently with no recovery route. New `backfillIgnoreCommentsFromComments_()` (`Shared_Classifiers.js`) closes the gap — manually run (like `Setup_Registry.js`'s other one-off repairs), not automatic, since checking comments costs an extra Trello API call per card and `.ignore` is rare enough not to justify that cost every sync. See `SCHEMA.md` §14.

## 2026-08-17 — Guided RTS Flow (Ship Date → Transit Type → Origin → Destination)

Source: direct user feedback that the Readiness/ETA feature was "ugly, and beyond vague" — the old free-text "Port of arrival" field gave no guidance, and there was no way to account for peak-season transit delays.

### Added

- **New detailed transit-lane engine**, sourced from the user's `Transit_Time` tab (48 real shipping lanes: Origin — China/Timing or CIS Florida — × Destination × Travel Type × Load Type × Season, with real day-count breakdowns). `findTransitLane_()`/`estimateShippingWindowV2()` (`Service_Dates.js`) replace guesswork with an actual lane lookup, and are now the first thing `resolveEtaAndBasis_()` tries (ahead of the older Config-sheet port-group math, which survives only as a fallback).
- **Peak-season awareness.** The user added `Peak_Start_Date`/`Peak_End_Date` cells to `Transit_Time!Q1:R2` (currently Aug 15 – Nov 15, month/day only — recurs annually). `isPeakSeasonForDate_()` checks the chosen ship date against this window and picks the matching `Season` row automatically.
- **Guided 4-step flow**, in both the inline Readiness & ETA panel and the standalone Shipping Estimate calculator: Ship Date → Transit Type → Origin → Destination (Port), each step's options filtered by the ones before it. A collapsed "Advanced: Load Type" selector defaults to the **slowest** matching lane — confirmed with the user: "we don't want to be optimistic in planning for shipping times." Most users never need to open it.
- **FedEx caveat note** — shown whenever Transit Type = FedEx/UPS/Truck: "these are based on shipping lanes, and may not reflect true times" (user's own words), since the FedEx rows in `Transit_Time` are reference lanes, not a live rate quote.
- **Live ETA preview** in the inline panel as the picker is filled in, before Save — same calculation the standalone calculator uses.

### Kept

- Both **Clear** buttons (Clear RTS in the inline panel, Clear in the standalone calculator) — explicitly requested to stay.
- The "Ready to ship" label/terminology (matches RTS conventions used throughout the rest of the app) — a short "(leaves origin)" hint was added under it instead of a full rename, to resolve the ambiguity without churning the term everywhere else it's used.

### Not changed

- The picker's Transit Type/Origin/Load Type selections are **not** persisted as new SHIPMENTS columns — only the resolved Port name is saved (into the existing `portOfArrival` column, unchanged), so the inline panel's picker starts unselected each time it's reopened. See `SCHEMA.md` §4G for the full reasoning and tradeoff.

## 2026-08-17 — Assembly Consolidation & Chain/Brand Registry Fixes

Source: the user added three new reference tabs to the live workbook — `Delivery_Address`, `Transit_Time`, `Order Process` — to refine the shipping calculator and document how product actually moves from supplier to customer. Reviewing them against `CUSTOMER_REGISTRY` and the separate `Assemblies.xlsx` workbook surfaced real, previously-undocumented bugs alongside the two features requested.

### Added

- **Consolidated Assembly recipe table.** The live `Assemblies` tab held a small 16-row hand-typed draft; the user's full recipe breakdown lived across 19 separate tabs in `Assemblies.xlsx` (one per assembly). `consolidateAssemblyRecipes()` (`Setup_Registry.js`) flattens all 19 into one 74-row table, resolving every component name against the `PRODUCT` sheet's canonical `Full QB SKU Name` the same way `resolveCanonicalItemName_()` does at receiving time. See `SCHEMA.md` §18 "Recipe Consolidation."

### Fixed

- **`getChainFromRecord()` (`JS_Handlers.html`) had no match precedence — first row in `CUSTOMER_REGISTRY` always won.** A Canada-bound Homesense or Marshalls card matches both the generic `TJX Cos.` row (`Local Warehouse`, earlier in the sheet) and the specific `TJX CA` row (`Virtual_Warehouse`, later) — it always resolved to the generic one, silently misgrouping it in the "Select All Chains/Brands" dropdown. Now does a two-pass match: any non-`"Local Warehouse"` row is checked before any `"Local Warehouse"` row, mirroring the precedence logic `classifyInboundOrderOrigin_()` (§4E) already used for inbound local/non-local classification.
- **The three `TJX CA` registry rows (Winners/Homesense/Marshalls) had corrupted `Regex_Aliases`** — leftover instruction text was literally appended after the real pattern, likely breaking the match entirely. Fixed to clean patterns; Homesense/Marshalls additionally require a co-occurring Canada signal (`CA`/`CANADA`/`RTF`/`TJXC`) via lookahead, since a bare brand-word pattern would otherwise now win over the correct US-local row for every US Homesense/Marshalls card too, given the precedence fix above.
- **TK Maxx was registered under a dead `"TJX UK"` bucket** with a regex requiring the literal word "AUSTRALIA," which can't match a plain "TK Maxx" card. `Order Process`/`Delivery_Address` both confirm TK Maxx is fulfilled through CREDO, the same third party as TJX Australia — repointed to `Parent_Account: "TJX AU"` with a working regex. Both fixes via `fixTjxCanadaAndTkMaxxRegistry()` (`Setup_Registry.js`) — run manually from the Apps Script editor, safe to re-run. See `SCHEMA.md` §9A.

### Not changed

- `Delivery_Address`/`Transit_Time`/`Order Process` are not read by any code — they served as the source of truth for the registry fixes above, not as a new runtime data source.

## 2026-08-14 — UI & Origin Filter Adjustments (revised same day — see note below)

### Fixed

- **RTS Panel unnecessary expansion.** The Readiness & ETA panel now only displays when the user explicitly clicks the "Date" column on an inbound shipment row. Clicking anywhere else on the row expands the line items and FedEx tracking normally, while keeping the RTS panel hidden (`toggleChildBoxRow()`/`renderReadinessPanel_()`, `JS_Handlers.html`). Collapsing the row rebuilds its content from scratch on next open, so it always resets to default. **Follow-up same day:** if the row was already open (e.g. opened via a body click, RTS hidden) and the user then clicked the date cell specifically to reveal RTS, the click was being read as a generic "close" and just collapsed the whole row instead of showing RTS — you had to close it fully and reopen via the date cell to actually see it. `toggleChildBoxRow()` now special-cases a date-cell click on an already-open row: it reveals/hides the RTS panel in place (via a `data-rts-panel` marker) instead of collapsing the row.
- **Filter text persisted across the Outbound/Inbound tab switch.** `switchLogisticsTab()` (`JS_Handlers.html`) never cleared the SKU/store-or-PO free-text search boxes — only the separate manual "Reset Filters" button did. Outbound and Inbound have different search vocabularies (SKUs/store names vs. PO numbers/suppliers), so a term typed on one side kept silently filtering the other tab's completely different rows. Tab switch now clears both text inputs.
- **Trello Injector was pulling every open board on the account, not just the 4 this app knows about.** `getTrelloBoards()` (`Service_Read.js`) called Trello's `/members/me/boards` with no filtering, so any stale/duplicate-named board sitting in the same Trello workspace (e.g. an old "Burlington..." board alongside the real, misnamed "Bulrington Shipping Schedule" — see the Punch list pass entry below) showed up in the Injector's board picker too, burning API calls/cache on boards nothing else in this app ever reads. Now filtered to `getBoardMatrix_()`'s known IDs (Script Properties), same source of truth `syncAllBoardsToShipmentsTab()` uses.

### Added

- **"Clear RTS" button.** The Readiness/ETA editor (`renderReadinessPanel_()`, `JS_Handlers.html`) now shows a Clear button next to Save whenever a ready-to-ship date is set — for when it was only ever an estimate and is no longer accurate. Blanks the date/basis inputs and saves; `updateShipmentReadiness()` (`Service_Dates.js`) already clears RTS_DATE/RTS_BASIS locally (no Trello write) whenever the date comes back empty, so no server change was needed.
- **Standalone Shipping Estimate calculator.** A new inbound-only "Shipping Estimate" button/modal (`View_Dashboard.html`) lets you enter a ready date + port + transit mode and see the computed ETA using the exact same port/transit-mode lead-time math as the Readiness/ETA panel (`estimateShippingWindow()`, `Service_Dates.js`, reusing `classifyPortGroup_()`/`addPortGroupLeadTime_()`/`leadTimeDaysForMode_()`) — but as a pure calculation: no cardId, no SHIPMENTS row, no sheet write, no Trello write. Has its own Clear button.

### Corrected same day (see note)

- **Inbound origin classifier keyword fallback — walked back from "removed."** An earlier edit this same day dropped the keyword fallback in `classifyInboundOrderOrigin_()` (`JS_Render_UI.html`) entirely and both this changelog and `SCHEMA.md` were written to say so — but confirmed with the user: `RTF`/`TJXC`/`TJX CANADA` (RTF is literally the physical Canadian warehouse) and `TJX AU`/`TJX TK`/`TJX UK` are genuine non-local destination signals, not vendor/freight-mode noise, and removing them would have reopened the exact `GEN6 SLIDE PB`-style bug Section 4E was built to fix (see `SCHEMA.md` §4E). The fallback is back, tuned to `\b(AUSTRALIA|AUS|TJX CANADA|TJXC|RTF GLOBAL|RTF|TJX AU|TJX TK|TJX UK)\b`. Only `TIMING` (a vendor/supplier name — doesn't indicate a destination) and bare `CANADA` (too generic, matched local orders that merely mentioned Canada) stay dropped from the original list. `SCHEMA.md` §4E has been corrected to match.

- **A card the user considered "delivered" was being archived as `"CARD DELETED FROM TRELLO"` instead.** Confirmed the user's actual completion workflow: check Trello's due-date checkbox ("marking complete" — this checkbox, `dueComplete`, is otherwise never read anywhere in this codebase, purely a UI signal to the user), manually move the card to a Delivered list, then archive/close the card in Trello. That last step makes the card vanish from the board's open-card fetch exactly the way a genuinely deleted card does, so `pruneDeletedShipmentCards_()` (`syncAllBoardsToShipmentsTab.js`) was recording every one of these as lost data instead of a completed shipment. New `resolveVanishedCardStatus_()` does one extra Trello lookup per vanished card to tell "archived by a human" (`closed: true` → now correctly written as `RECEIVED`/`DELIVERED`) apart from "moved to an untracked board" (`MOVED OFF TRACKED BOARD`) and genuinely deleted/unreachable (unchanged `CARD DELETED FROM TRELLO`). See `SCHEMA.md` §11A.
- **`.ignore` can now be a Trello *comment*, not just a label.** The label mechanism (`PORTAL: IGNORE`) still exists and is still the only thing anything actually checks, but attaching a label was confirmed too heavyweight for what's meant to be a quick toggle. A plain `.ignore` / `.unignore` comment on a card (either direction) now drives the same label on/off automatically in real time (`parseIgnoreComment_()`/`applyIgnoreDeclaration_()`, `Shared_Classifiers.js`, wired into `Webhook_Receiver.js`'s `commentCard` handling) — same "comment as trigger, label as storage" pattern the READY/PORT feature already uses.

### Clarified — not a bug

- **`dueComplete` (Trello's due-date checkbox) is intentionally never read as a status input**, even though it's what the user means by "marking complete" — see the archival fix above for why that's fine (the checkbox itself was never the missing signal; the archive-on-close step was).

## 2026-08-14 — Punch list pass

Source: full-repo audit (61 pulled source files, `SCHEMA.md`, live workbook, live Trello exports across all 4 boards, a diagnostic scrape, and a Script Properties dump).

### Fixed

- **Outbound chain classification never matched abbreviated store codes.** `CUSTOMER_REGISTRY` required the full brand word (`\bMARSHALLS\b`, etc.), but real Shipping Schedule cards use codes like `MAR 1670` / `SIE 256` / `HS 2044` / `HG 1246` / `OFF Store 6831` — none matched, so most TJX-family and AEO Offline cards fell through to `OTHER`. Added abbreviation aliases (`Setup_Registry.js`: `fixCustomerRegistryAbbreviations()`, plus a general-purpose `updateCustomerRegistryRegex(brandId, alternatePattern)` helper for future rows). Two-letter codes are anchored to start-of-string to avoid false-positive collisions with product text.
- **Burlington board-name fallback was dead.** The live Trello board is actually named "Bulrington Shipping Schedule" (transposed letters), so the `.includes("BURLINGTON")` fallback in `getChainFromRecord()` (`JS_Handlers.html`) could never fire. Now matches both spellings.
- **Inbound "In Transit / Active" badge counted un-shipped cards and its click-filter was a dead end.** It counted on `rollupStatus.includes("IN TRANSIT")`, a string that's outbound-only — inbound rows sitting in "Ordered"/"In Production" with zero movement were counted as active. The click-filter searched literal text "IN TRANSIT," which never appears in an inbound row. Both now key off the real `getInboundLifecycleStage() === "ON THE WAY"` stage (`JS_Handlers.html`).
- **Outbound "Shipped / Done" badge's click-filter was also a dead end**, for two stacked reasons: it searched literal text "SHIPPED" (rarely present — completed rows usually show `PACKED`/`STAGED`, and anything that actually reaches `SHIPPED` gets archived out of the live view almost immediately), and the default "hide completed" filter blanked the results regardless. Badge now uses a dedicated status match and auto-enables "show completed" (`JS_Handlers.html`).
- **Date-range column sort put date-less rows before the earliest real date.** Clicking the Scheduled Date column header computed `new Date('').getTime() || 0` for rows with no date, landing them at epoch-0 — first in ascending order. Now sorts date-less rows to the end regardless of sort direction (`JS_Handlers.html`, `handleSort()`).
- **Scheduler could wedge itself indefinitely.** `window.isEditing`, set from ~20 `onfocus`/`onblur` pairs across three files, could get stuck `true` forever if a focused input's DOM node was replaced by a repaint before `blur` fired (observed on iOS Safari) — the polling scheduler would then log "paused (UI busy)" forever with no user interaction. `window.isEditing` is now a property with a getter/setter (`JS_Store.html`) that timestamps every write; `uiIsBusy()` self-heals a value stuck `true` for more than 2 minutes.
- **Inbound origin classifier couldn't see Trello labels.** `classifyInboundOrderOrigin_()` only scanned `entityName` + checklist-derived `summary`, never labels — a card labeled `TJX CANADA` / `RTF GLOBAL` with an empty checklist was invisible to the AUS/CANADA/RTF/TIMING keyword scan and defaulted to Local Warehouse. `formatInboundLineItems()` (`Webhook_Receiver.js`, `syncAllBoardsToShipmentsTab.js`) now appends label names to the summary text so the classifier can see them. Takes effect on a card's next webhook touch or the next full sync.
- **Port lead-time math had two independent sources of truth that silently disagreed.** The `Config` sheet's hand-maintained port table was never read by anything — `Service_Dates.js` ran its own separate hardcoded numbers (LA 39 days total, Miami 47) that didn't match the sheet (LA 29, Miami 43). `getPortGroups_()` (`Service_Dates.js`) ran the old hardcoded object survives only as `PORT_GROUPS_FALLBACK`, used solely if the sheet is unreadable. New port rows (e.g. `Canada[Toronto]`) are picked up automatically, no code change needed.
- **Port lead-time legs were summed as flat calendar days, but only one of the three legs actually works that way.** Confirmed with the user: "Estimated Departure" and "Clearance, Delivery" are true business-day counts (skip Sat/Sun, no holiday calendar); "Port to Port" is calendar days (the ship doesn't stop for weekends). `addPortGroupLeadTime_()` now walks the three legs in order with the correct arithmetic for each (`addBusinessDays_()` vs. `addDays_()`) instead of summing into one total — real elapsed time from Ready-to-Ship to ETA now correctly varies by day-of-week instead of being a fixed constant.
- **Duplicate `View_FedEx` include produced three elements sharing `id="fedex-view"`.** `Index.html` included it twice, once bare and once in an extra wrapper `<div id="fedex-view">` — but `View_FedEx.html` already self-wraps with that same id, so the wrapper was a third duplicate, not a second. Reduced to one bare include, matching every other view's pattern.
- **Dead duplicate `parseDateToTimestamp()`.** Defined in both `JS_Render_UI.html` and `JS_Handlers.html`; since `JS_Handlers.html` loads second, its copy silently won everywhere and the earlier one never ran. Removed the dead copy.
- **Dead duplicate `formatInboundLineItems()`** (found while fixing the label pass-through above) — identically defined in `Webhook_Receiver.js` and `syncAllBoardsToShipmentsTab.js`, same shadowing hazard as above. Kept both in sync rather than removing one, since both files are legitimate independent entry points (webhook vs. scheduled sync).
