## Phase 0 — Guardrails (do first, ~1 hour, prevents regressions in every later phase)

**0.1 — Add a duplicate-global detector.** Apps Script has one global namespace per side (server `.js` files; client `<script>` blocks). A redefinition silently shadows — last-loaded file wins. The README already documents this biting the project twice. Add `tools/check-globals.sh` (or a `clasp push` wrapper) that fails when the same top-level `function name(` appears twice within the server set or twice within the client set. Working detector:

```bash
grep -n -H -E "^function\s+[A-Za-z_$][A-Za-z0-9_$]*\s*\(" *.js | sed -E 's/^([^:]+):([0-9]+):function\s+([A-Za-z0-9_$]+).*/\3\t\1:\2/' | sort | awk -F'\t' '{print $1}' | uniq -d
```

Run the same over `JS_*.html View_*.html Index.html` with a leading-whitespace-tolerant pattern. It currently reports exactly the three items in Phase 4 (C1, C2).

**0.2 — Add a `res.success` lint.** Grep for `google.script.run` chains whose success handler never inspects `res`. There are ~7 today (see A2). A one-off script is fine; the point is to keep Phase 1's fixes from rotting.

## Phase 1 — Silent failures on the write path (**Critical** — do this first)

This is the cluster that makes an operator tap SET, see nothing happen, and tap again.

### A1. `modifySheetRow()` no-ops when the row isn't found, and its callers still report success

`Service_Write.js:643` — `modifySheetRow()` ends with `if (targetRowIdx > -1) { ...write... }` and **no `else`**. When the location / SKU / instanceId doesn't resolve it returns `undefined` having written nothing. Every caller then unconditionally returns success:

- `setTotalStock()` — `Service_Write.js:158` → `return { success: true };` (line 178)
- `updateStock()` — `Service_Write.js:181` → `return { success: true };` (line 203)
- `updateInventoryField()` — `Service_Write.js:596`
- `updatePalletComment()` — `Service_Write.js:603`
- `reservePallet()` — `Service_Write.js:638`

**Failure scenario (confirmed from code):** operator opens a pallet whose row was deleted or shifted by the concurrent sync between page load and tap. SET writes nothing, server says `{success:true}`, `refreshData()` repaints the old number. Operator re-taps; still nothing. No log, no toast, no `Audit_Log` entry.

**Fix:** `modifySheetRow` returns `{success:false, error:'Row not found for <loc>/<sku>'}` when `targetRowIdx === -1` and `{success:true}` otherwise; every caller returns that result verbatim instead of a hardcoded literal.

### A2. Client mutation handlers have no failure handler and ignore `res.success`

`JS_Handlers.html:3407–3432` — five of the six inventory mutations on the drawer (the Qty / − / + / SET / comment controls visible in screenshot 3):

```js
google.script.run.withSuccessHandler(() => { refreshData(); }).setTotalStockByRow(rowIdx, locId, sku, cleanVal);
```

No `.withFailureHandler`, and the success handler never reads `res`. So `updateInventoryByRow`'s real error returns — `"Row data mismatch. The sheet may have been modified."` (`Service_Write.js:857`) and `"Server busy. Please try again."` (`Service_Write.js:889`) — are **both discarded**. Affected: `updateItemField`, `setTotal`, `adjustStock`, `savePalletComment`.

**Fix:** route all five through one helper that checks `res && res.success !== false`, calls `showToast(res.error, 'error')` on failure, and attaches `.withFailureHandler`. `showToast` already exists at `JS_State.html:26`. The pattern to copy is `explodePartialHub`'s handler at `JS_Handlers.html:3389–3405`, which already does this correctly.

### A3. `receivePOCardItems` reports success even when nothing reached Trello

`Service_Write.js:1012`. Inventory rows are appended under a lock (line 1153), then:

- checklist PUTs — `Service_Write.js:1184–1191`: `muteHttpExceptions: true` **and** `catch(e){}`, response code never inspected
- comment POSTs — `Service_Write.js:1198–1210`: same
- receipt email — `Service_Write.js:1225–1232`: `catch(e){}`

then `return { success: true, ... }` at line 1302 regardless.

**Failure scenario:** Trello token expires or returns 429 mid-batch. Inventory gains the units, the Trello checklist still shows the full remaining QTY, the operator sees a success toast, and the next shift receives the same PO again. Inventory double-counts with no error anywhere.

**Fix:** collect per-item `getResponseCode()`; return `{success:true, trelloSynced:false, failedItems:[...]}` when any non-2xx occurs, and surface it in `submitBulkPOReceipt`'s handler (`JS_Handlers.html:4429`) as a distinct warning state — not a plain success.

### A4. `getAllInventory()` returns `null` on error; two callers then throw into their own swallow

`Service_Read.js:376–402` returns `null` in its catch (line 400). Callers:

- `getInventoryTotals()` — `Service_Read.js:417` does `data.forEach(...)` → TypeError → caught at line 585 → `return {}`. Result: the Inbound Report's On Hand column shows `no match` for every item, presented as a data finding rather than a fetch failure.
- `getAuditWorklist()` — `Service_Read.js:743` does `inventory.filter(...)` → caught at line 758 → `return []`. Result: **an empty audit worklist reads as "nothing to audit."**

**Fix:** make `getAllInventory()` throw (it's already wrapped by `precompileDataset_` at `Service_Router.js:46`, which logs to `BOOT_ISSUES_` and falls back to `[]` correctly), or return `[]` consistently. Then give both callers an explicit `if (!data) throw new Error(...)`.

### A5. ~40 empty `catch(e){}` blocks

Highest-value clusters: `Service_Assembly.js` (lines 44, 96, 139, 207, 278, 362, 377, 454) and `Service_Write.js` (53, 62, 72, 110, 267, 281, 295, 682, 1196, 1211, 1231). Most wrap `JSON.parse(comment.split('_SYS_')[1])` — a malformed `_SYS_` blob silently makes a Master Hub row invisible to explode/move logic.

**Fix:** don't add a `throw` to all of them; add `Logger.log`, and for the `_SYS_` parsers introduce a single shared `parseSysBlob_(comment)` helper in `Shared_Classifiers.js` that logs the row and raw text once on failure. That replaces ~15 duplicated try/catch sites with one auditable path.

### A6. `doPost` always returns HTTP 200, so Trello never retries

`Webhook_Receiver.js:28–31` — the catch returns `ContentService.createTextOutput("ERROR")`, which is a **200 response with the body "ERROR"**. Trello only retries on non-2xx. Every webhook that throws is permanently lost and invisible until the next scheduled sync.

**Fix:** log failures to a `Webhook_Errors` tab (Apps Script can't set a non-200 status from `ContentService`, so a durable error log is the actual remedy) and alert on non-empty.

### A7. The 3-second webhook debounce drops events instead of deferring them

`Webhook_Receiver.js:19–22` — the second event for a card inside 3s returns `"OK - Debounced"` and is discarded. Moving a card and adding a label in quick succession loses the second change until the next full sync.

**Fix:** store the latest payload in cache under the lock key and process it on release, or narrow the debounce to guard only against *identical* payloads (hash `action.data`), not any second event.

### A8. No 429 / rate-limit handling on any Trello call

Confirmed: zero occurrences of `429`, `retry`, or `backoff` across all `.js` files. `receivePOCardItems` issues 2 requests per checklist item with no cap; Trello's limit is 100 req/10s per token. A 40-line PO receipt is 80 requests in a tight loop.

**Fix:** a shared `trelloFetch_(url, opts)` in `Shared_Classifiers.js` with exponential backoff on 429/5xx and a returned status the caller can act on. Route the 20 `UrlFetchApp.fetch` Trello calls in `Service_Read.js` and the 12 in `Service_Write.js` through it.

## Phase 2 — Data integrity at the Sheets boundary (**High**)

### B1. `valueInputOption: "USER_ENTERED"` on every batch write

`Service_SheetsAPI.js:29` and `:58`. Any value written this way that starts with `=`, `+`, `-`, or `'` is **parsed as a formula, or has its leading quote stripped**. Pallet comments and PO checklist descriptions are free text from Trello.

**Failure scenario:** a checklist item named `-3M SLIDE`, or a comment `=2 pallets short`, becomes `#NAME?` in the Inventory sheet permanently.

**Fix:** `"RAW"` for both. Nothing in this codebase writes an intentional formula through `SS_API`.

### B2. `Values.append` with `"<sheet>!A1"` and no `insertDataOption`

`Service_SheetsAPI.js:65–70`. The API default is `OVERWRITE`, and the A1 range makes it table-detect from the top. A blank row anywhere in Inventory truncates the detected table, so the append lands mid-sheet and overwrites live rows.

**Fix:** pass `insertDataOption: "INSERT_ROWS"`.

### B3. `explodeAssembly` is four non-atomic API calls

`Service_Assembly.js:283–290` — `batchUpdateValues` → `batchAppendRows` → `batchAppendRows` → `batchDeleteRows`. A quota error or 6-minute timeout between calls 2 and 4 leaves the components restored **and** the assembly rows still present: inventory silently doubles.

**Fix:** collapse into a single `Sheets.Spreadsheets.batchUpdate` with `updateCells` + `appendCells` + `deleteDimension` requests — that call is atomic. Ordering constraint: deletes must be descending (already handled at `Service_SheetsAPI.js:76`) and must come after the appends.

### B4. `restoreItemToSheet`'s append path doesn't update the in-memory snapshot

`Service_Assembly.js:246–253`. The update and vacant-reuse paths both mutate `data[i]`; the `sheetAppends.push(...)` path (line 249) does not. Two components restoring to the same previously-unknown location produce two separate rows instead of one merged row.

**Fix:** push the synthetic row onto `data` as well, so the next iteration finds it.

### B5. `NaN` reaches `setValue()`

`JS_Handlers.html:3411` — `Number(rawVal.replace(/,/g, ''))` with no `isNaN` guard. Server-side, `Service_Write.js:159` and `:907` both branch on `newQty <= 0`, which is **false for NaN**, so execution falls through to the else and writes `NaN` into column C.

**Fix:** guard on the client (`if (!Number.isFinite(cleanVal) || cleanVal < 0) return showToast(...)`) **and** on the server (reject non-finite in `setTotalStock` / `setTotalStockByRow` / `updateStock` / `updateInventoryByRow`). Separately, decide deliberately whether typing `0` should delete a pallet — today it does, with no confirmation.

### B6. The over-receipt guard trusts client-supplied quantities

`Service_Write.js:1024–1032` computes `originalExpectedQty` from `item.oldQty` / `item.oldRcvd`, which arrive **from the browser**. Two stations with the page open on the same PO both hold the same stale `oldRcvd`, both pass the guard, and both append.

**Fix:** re-read the card's live checklist via `getExistingCardChecklist(cardId)` (`Service_Read.js:1431`) inside the lock and validate against that, not the client payload.

### B7. `modifySheetRow` has no `LockService`

`Service_Write.js:643`. Its `*ByRow` twins (`updateInventoryByRow:846`, `setTotalStockByRow:896`) both take `LockService.getScriptLock()`. `modifySheetRow` reads `getDataRange().getValues()`, computes, then writes — completely unguarded.

**Fix:** wrap in the same `tryLock(10000)` pattern, and return the "Server busy" error rather than silently proceeding.

### B8. `logDisplayDiagnostic` writes into the `Config` sheet

`Service_Write.js:944–956` appends `[Date, width, height, userAgent]` to the same `Config` sheet that holds the hand-maintained port lead-time table (`Service_Dates.js:207`) and `STAKEHOLDER_EMAILS` (`Service_Write.js:1043`). Two problems: unbounded growth inside a hand-edited operational table, and — if `Config` is ever missing — line 949 **creates it with diagnostic headers**, permanently breaking `getPortGroups_`.

**Fix:** move diagnostics to their own `Diagnostics` tab. The README already lists this split as a known cleanup item; this is the concrete reason to do it.

### B9. Raw `Date` cell values render as entity names

Screenshot 4 shows a calendar chip reading **`Mon Mar 01 1666 00:0`** — a JS `Date` stringified into the entity-name slot. `getValues()` returns real `Date` objects for any cell Sheets auto-parsed as a date, and nothing between the sheet read and `JS_Handlers.html:763`'s `escapeHtml(cleanStoreEntityName(item.entityName || ...))` type-checks it.

**Fix:** coerce SHIPMENTS text columns with an explicit `String()` / `instanceof Date` guard at the read boundary in `buildLogisticsDashboardPayload_` (`Service_Read.js:98`), and have `cleanStoreEntityName` reject a value that stringifies to a Date. Separately, find and fix the source cell — that is real data sitting in the ledger.

### B10. `formatCleanDate` invents dates from arbitrary text

`JS_Handlers.html:276–288` — anything not matching `MM/DD/YYYY` falls through to `new Date(str)`, which happily parses fragments. `parseDateToTimestamp` (line 290) then does the same again on its fallback path.

**Fix:** whitelist the accepted formats and return `null` for everything else, so an unparseable date surfaces as `—` instead of a plausible wrong date on the calendar.

## Phase 3 — Mobile UI (**High** usability — safe to pull ahead of Phases 1–2)

Every item below ties to one of the five screenshots or to a specific rule in `Styles_Responsive.html` / `Styles_Base.html`.

### E1. The whole app is ~46px taller than the viewport on mobile

`Styles_Base.html:66` — `#main-container { height: calc(100vh - 54px) }`. But `#top-ui` (`Styles_Base.html:13`) is `height: auto; min-height: 54px`, and at ≤768px `Styles_Responsive.html:56` gives `#search-container { flex: 1 1 100%; order: 10 }`, wrapping the search bar onto its own row — roughly 100px tall, not 54px. Because `body` is `overflow: hidden` (`Styles_Base.html:9`), the bottom ~46px of every view is **unreachable**. Visible in screenshot 3: the `MOVE TO...` button is clipped at the fold.

**Fix:** delete the `calc()`. `body` is already `display:flex; flex-direction:column`, so `#main-container { flex: 1 1 auto; min-height: 0; }` does the right thing at every width. Also swap the base `100vh` → `100dvh` — the mobile override at `Styles_Responsive.html:70` already uses `dvh`, the base rule doesn't.

### E2. Modal shells use `100vh` / `88vh` — iOS Safari clips the footer

`View_Dashboard.html:187` (`height: 100vh`, inner `max-height: 88vh`), `:219`, `:271`, `Index.html:213`, `View_FedEx.html:32` and `:73`. On iOS `100vh` is the *expanded* viewport, so the action row sits under the browser chrome. Screenshots 1 and 2 show the Print/Close footer jammed against the Safari toolbar with content cut behind it.

**Fix:** `height: 100dvh` on the overlay, `max-height: 88dvh` on the panel, and `padding-bottom: env(safe-area-inset-bottom)` on the footer row. The carry bar at `Styles_Responsive.html:150` already does the `env()` part correctly — copy that pattern.

### E3. The Inbound Report's PO table has no horizontal scroll container

`JS_Render_UI.html:1774` emits `<table style="width:100%">` directly into `#inbound-report-content`, whose only overflow rule is `overflow-y: auto` (`View_Dashboard.html:202`). The status badge cell (`JS_Render_UI.html:1795`) has a hard min-content width that pushes the table past 375px — **so the "Received" column is clipped off the right edge with no way to scroll to it**, and the PO name wraps one word per line. That is exactly screenshot 1.

**Fix:** wrap the table in `<div style="overflow-x:auto; -webkit-overflow-scrolling:touch;">` and give the table `min-width: 480px`. Better for this screen size: below 600px render each PO as a stacked card (PO name on its own line, Status / Expected / Received as a 3-up row) instead of a table.

### E4. The calendar grid blows past the viewport

`View_Dashboard.html:171` — `grid-template-columns: repeat(7, 1fr)`. `1fr` resolves to `minmax(auto, 1fr)`, and the day chips at `JS_Handlers.html:767` are `white-space: nowrap`, so each column's min-content width is its longest chip. The grid grows to roughly 1100px. Screenshot 4 confirms: only Sun and Mon visible, cells ~150px wide, no scroll.

**Fix (two parts):** `repeat(7, minmax(0, 1fr))` stops the blowout immediately. But a 7-column month grid at 375px gives ~44px per cell, which can't hold a store name — below 600px, replace the grid with a vertical agenda list (date heading + that day's chips), which is what a phone user actually wants here.

### E5. The floor maps are unreadable on a phone, and the documented workaround is disabled

`Map_PWH_Floor.html:1` is an 878.85mm × 566.66mm plan. At ≤768px `Styles_Responsive.html:85` scales it to `width: 100%`, i.e. ~375px — each pallet slot lands around 8px. Screenshot 3 shows the result.

The comment at `Styles_Responsive.html:74–82` explicitly says *"Native pinch-zoom (touch-action: auto) is the way to inspect small map detail now."* But `Service_Router.js:57` sets the viewport to `maximum-scale=1.0, user-scalable=no`. iOS Safari ignores that (which is why screenshot 5 shows a zoomed map at all) — **Android Chrome honors it, so the documented mobile map workflow is broken there.**

**Fix:** make this consistent. Either drop `maximum-scale` / `user-scalable` from the viewport meta — the `<input>` auto-zoom that flag was guarding against is already handled by `Styles_Responsive.html:117`'s `font-size: 16px !important` — or add explicit +/−/reset zoom controls over `#map-container` and stop relying on native pinch. I'd recommend the former: one line, and it restores the behavior the CSS comment already assumes.

### E6. Touch targets are below the 44px minimum

`Styles_Responsive.html:127` — `#detail-view button, #detail-view select, #detail-view input { min-height: 32px !important; height: 32px !important; padding: 2px 8px !important; }`. That's the Qty / − / + / SET row in screenshot 3, plus `.btn-plus` / `.btn-minus` pinned to 32px wide at line 154. Apple HIG and WCAG 2.5.5 both call for 44px. This is a gloved-hands warehouse app.

**Fix:** raise to 44px in `#detail-view` and for `.btn-plus` / `.btn-minus`. The vertical room comes free once E1 is fixed.

### E7. Tooltip-only information is unreachable on touch

27 `title="..."` attributes across `JS_Handlers.html` / `JS_Render_UI.html` / `View_Dashboard.html`, 6 `:hover` rules, 6 inline `onmouseover`. The worst case is the Inbound Report's discrepancy explanation (`JS_Render_UI.html:1751`) — a multi-sentence explanation of *why* On Hand differs from Received, reachable only by hovering. Screenshots 1 and 2 show the ⚠ and ? icons with no way to read them.

**Fix:** make the ⚠ / ? icons tappable, opening the same text in a small popover or the existing toast. At minimum, tie them to a `<details>` disclosure like the "Which ones?" pattern already used at `JS_Render_UI.html:1668`.

### E8. The dashboard table forces horizontal scroll on every phone

`View_Dashboard.html:143–147` — fixed `th` widths of 40 + 150 + 180 + 150 = 520px before the flexible Entity column. `.table-wrapper` does set `overflow-x: auto` inline (line 137), overriding the class's `overflow: hidden` at `Styles_Components.html:166`, so it scrolls rather than clips — but every row needs two-axis scrolling to read.

**Fix:** below 768px, drop the fixed widths and move Scheduled Date + Status into the expanded child row, or render rows as stacked cards. Separately fix the dead `overflow: hidden` in `Styles_Components.html:166` — it's a trap for any `.table-wrapper` that doesn't happen to carry the inline override.

### E9. The drawer handle tab overlaps the map

`Styles_Responsive.html:112` positions `.drawer-handle-tab` at `top: -26px`, so the red chevron sits on top of the bottom edge of the map — visible mid-image in screenshot 3.

**Fix:** reserve 26px of padding-bottom on `#map-container` while the drawer is open, or move the handle inside the drawer's own header row.

### E10. `window.print()` won't work reliably from the modal footer

`View_Dashboard.html:209`. The app runs inside Apps Script's sandboxed iframe on `*.googleusercontent.com`; iOS Safari's print from a cross-origin iframe is unreliable, and the button gives no feedback either way.

**Fix:** below 768px, replace Print with the existing export path, or open the report content in a new tab (`window.open` + `document.write`) before printing.

### E11. 40px of a 375px screen goes to nested padding

`View_Dashboard.html:187` overlay `padding: 20px` plus `#inbound-report-content` `padding: 20px` (line 202). Compounds E3.

**Fix:** below 600px — overlay `padding: 0`, panel `max-width: 100%; border-radius: 0`, content `padding: 12px`. A full-bleed sheet rather than a shrunken desktop dialog.

## Phase 4 — Global-namespace duplication (Medium)

### C1. `formatInboundLineItems` is defined twice, server-side

`Webhook_Receiver.js:365` and `syncAllBoardsToShipmentsTab.js:312`. **Byte-for-byte identical today**, including the comment block. Whichever file Apps Script loads last wins for *both* callers, so an edit to the wrong copy silently does nothing. The README documents this exact function as having caused a real bug already.

**Fix:** move it to `Shared_Classifiers.js` (both files already depend on that for `isCardIgnored_`) and delete both copies.

### C2. `harvestSymmetricLayoutStructures` and `calculateEmptyLayoutMetrics` are defined twice, client-side

`JS_Handlers.html:3094` / `:3115` and `JS_Render_Core.html:350` / `:371` — also identical. `Index.html:231–233` loads `JS_Render_Core` before `JS_Handlers`, so **the `JS_Render_Core` copies are dead** and any edit to them has no effect.

**Fix:** delete the `JS_Render_Core.html` copies — they're the shadowed pair. Note the neighbouring `heatmapClassFor` at `JS_Handlers.html:3087` carries a comment claiming it's shared "so the logic lives in exactly one place"; these two functions violate that intent directly.

### C3. Not-actually-duplicates, confirmed — do not "fix" these

Recorded so a future pass doesn't churn on them. `explodeAssembly` (`JS_Handlers.html:3346` vs `Service_Assembly.js:186`) and `findEffectiveQtyPer_` (`JS_Render_UI.html:141` vs `Service_Assembly.js:314`) are client/server pairs in **separate namespaces** — fine. `restoreItemToSheet` appears twice in `Service_Assembly.js` (218, 398) but both are **nested inside** their enclosing function — also fine.

## Phase 5 — Security (**High**, but needs a deployment decision first)

### D1. Anonymous access to every write function

`appsscript.json` — `"executeAs": "USER_DEPLOYING"`, `"access": "ANYONE_ANONYMOUS"`, and there is no auth check in `doGet` (`Service_Router.js:18`) or in any `Service_Write.js` entry point. **Anyone with the /exec URL can call `setTotalStock`, `removeItemFromLocation`, `moveInventoryItem`, `receivePOCardItems` and the rest via `google.script.run`, executing as the deploying account.**

This looks like a deliberate configuration (warehouse floor devices, no Google sign-in), so the fix is a product decision, not a pure code change. Options, in order of preference:

1. Switch to `ANYONE` (requires a Google account) or `DOMAIN`, and drop the anonymous path entirely.
2. Keep the anonymous `doGet` but require a shared secret: a `?k=` token in the URL checked in `doGet`, stamped into the page, and re-validated at the top of every write function.
3. At minimum, add a station-token check to the five most destructive writes.

**This is the one finding I'd want an explicit decision on before implementing** — option 1 changes how every floor device signs in.

### D2. `doPost` accepts unauthenticated, unverified payloads

`Webhook_Receiver.js:1`. No Trello webhook HMAC verification. Anyone can POST a crafted `{action:{data:{card,list,board}}}` and write arbitrary rows into `SHIPMENTS`.

**Fix:** verify Trello's `X-Trello-Webhook` header (base64 HMAC-SHA1 of `body + callbackURL` using the API secret) before processing. Note the README says webhooks currently route through a Render intermediary (`Webhook_Receiver.js:369`) — check what that server forwards before choosing where the verification lives.

### D3. Server JSON is injected raw into a `<script>` block

`Index.html:22–30` — `window._serverInventory = <?!= precompiledInventory ?>;` and eight siblings. `JSON.stringify` does not escape `<`, so **any cell containing the literal `</script` terminates the script tag early and breaks the entire page load** with no error surfaced. Pallet comments and PO summaries are free text.

**Fix:** in `precompileDataset_` (`Service_Router.js:196`), append `.replace(/</g, '\\u003c')` (and handle ` ` / ` `) to the stringify result. One line, covers all nine injections.

### D4. Unescaped sheet/Trello data in `innerHTML` and in `title` attributes

`escapeHtml` exists and is correct (`JS_State.html:11`) and is used in ~40 places — but the Inbound Report renderer skips it entirely: `itemName` (`JS_Render_UI.html:1765`), `po.poName` (`:1791`), `o.summary` (`:1826`), and the whole `discrepancyTitle` string interpolated into `title="..."` at `:1751` (a `"` in an item name breaks the attribute outright).

**Fix:** wrap all four in `escapeHtml`, then grep `JS_Render_UI.html` for remaining raw concatenations of `item.*` into `innerHTML` — that file has the lowest `escapeHtml` coverage of the render layer (0 uses vs. 26 in `JS_Handlers.html`).

### D2 (historical) — why the audit's originally-prescribed fix is BLOCKED BY THE PLATFORM as written. Read this before attempting a different approach.

**The finding's prescribed fix cannot be implemented in Apps Script.** It says to
verify Trello's `X-Trello-Webhook` header inside `doPost`. Apps Script web apps
**cannot read request headers at all** — the `doPost(e)` event object exposes
only `postData`, `parameter`, `parameters`, `queryString`, `pathInfo`,
`contextPath` and `contentLength`. There is no headers field, and no workaround
from inside the script.

Compounding it, and confirming the finding's own caveat: webhooks do not come
from Trello directly. `setupWebhooksForAllBoards()` (`Webhook_Receiver.js`,
grep for `onrender`) registers the callback as
`https://trello-webhook-server-763h.onrender.com/trello-webhook`, so the path is

```
Trello  ->  Render intermediary  ->  Apps Script doPost
```

That has two consequences:

1. The HMAC Trello signs is over `body + callbackURL` where `callbackURL` is the
   **Render** URL, not the `/exec` URL. Even with the header in hand, Apps
   Script isn't the right place to check it.
2. The Render server is **not in this repo**, so the real verification point is
   somewhere this codebase can't reach.

**What to actually do, in order:**

- **Primary fix, on the Render server (outside this repo):** verify
  `X-Trello-Webhook` there — base64 HMAC-SHA1 of `rawBody + callbackURL` using
  the Trello API *secret* (not the token), compared constant-time. Reject
  non-matching requests before forwarding. This is the fix that closes the
  actual hole.
- **Secondary, inside Apps Script:** authenticate the Render → Apps Script hop,
  which is all `doPost` can see. Two options, both usable since query params
  *are* visible via `e.parameter`:
  - a shared secret the Render server appends (`?k=…`), checked in `doPost`;
  - or have Render forward Trello's signature as `?sig=…` plus the original
    `callbackURL`, and verify the HMAC in Apps Script with
    `Utilities.computeHmacSignature(Utilities.MacAlgorithm.HMAC_SHA_1, body + callbackUrl, secret)`
    then `Utilities.base64Encode`.

  Either way, **gate it on a Script Property being present** so the check is
  inert until the Render side is actually sending it — otherwise turning this on
  silently drops every webhook, and per A6 a dropped webhook is invisible until
  the next scheduled sync.
- Whatever lands, log rejections to the `Webhook_Errors` tab that A6 added
  (`logWebhookError_()`), so a misconfigured secret is visible rather than
  silent.
